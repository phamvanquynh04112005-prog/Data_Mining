3.3. Cách xử lý 3 lỗi thực tế thường gặp trên Windows (Đã giải quyết triệt để)
------------------------------------------------------------------------------
- LỖI 1: Cài PostgreSQL qua winget không hiện bảng nhập mật khẩu nên không biết
  mật khẩu của user 'postgres' (báo lỗi: password authentication failed for user "postgres").
  -> CÁCH GIẢI QUYẾT:
     Viết script tự động sql/setup_local_db.ps1 chạy bằng quyền Administrator.
     Script này tự động chỉnh file cấu hình C:\Program Files\PostgreSQL\16\data\pg_hba.conf
     từ 'scram-sha-256' sang 'trust' cho kết nối nội bộ (127.0.0.1/32 và ::1/128),
     chạy pg_ctl reload để nạp lại cấu hình không cần khởi động lại máy, sau đó
     đặt lại mật khẩu cho 'postgres', tạo role 'dm' (mật khẩu 'dm') và tạo
     database 'dm_course' với quyền sở hữu thuộc về 'dm'.

- LỖI 2: Windows PowerShell 5.1 đọc nhầm tiếng Việt UTF-8 không BOM trong file .ps1
  thành mã Windows-1252 làm vỡ dấu ngoặc kép.
  -> CÁCH GIẢI QUYẾT:
     Chuẩn hóa toàn bộ thông báo console trong các file script PowerShell
     (sql/setup_local_db.ps1, sql/run_warehouse.ps1, sql/run_olap_and_views.ps1)
     về ký tự ASCII chuẩn, đảm bảo chạy ổn định trên mọi máy Windows.

- LỖI 3: Công cụ psql trên Windows mặc định dùng bảng mã console WIN1252 nên khi
  chạy file .sql có chú thích tiếng Việt UTF-8 bị báo lỗi:
  "character with byte sequence 0x9d in encoding WIN1252 has no equivalent in encoding UTF8".
  -> CÁCH GIẢI QUYẾT:
     + Đặt lệnh `SET client_encoding = 'UTF8';` ở dòng đầu tiên của tất cả các
       file .sql (01-staging.sql, 02-star-schema.sql, 03-transform.sql,
       04-dashboard-views.sql, 05-load-model-scores.sql, olap_queries.sql).
     + Đặt `$env:PGCLIENTENCODING = "UTF8"` trong các script PowerShell.

4. HƯỚNG LÀM & TƯ DUY THIẾT KẾ KHO DỮ LIỆU (STAR SCHEMA, ETL, OLAP, VIEWS)
================================================================================

4.1. Tại sao thiết kế Star Schema gồm 1 Fact + 4 Dimensions?
------------------------------------------------------------
Tập dữ liệu gốc creditcard.csv (ULB Kaggle) đã bị ẩn danh hóa qua phép biến đổi
PCA (28 cột V1..V28), chỉ còn 3 cột có ngữ nghĩa trực tiếp là Time (số giây
trôi qua tính từ giao dịch đầu tiên, 0..172792s ~ 48 giờ), Amount (số tiền giao
dịch) và Class (0 = Hợp lệ, 1 = Gian lận).
Để xây dựng một Star Schema chuẩn mực (yêu cầu tối thiểu 1 Fact + 3 Dimensions)
mà KHÔNG vi phạm nguyên tắc học thuật (không được bịa tên nghiệp vụ cho V1..V28,
không được gán ngày tháng lịch thực tế cho Time), kho dữ liệu được thiết kế gồm:

1) Bảng sự kiện trung tâm: Fact_Transaction (284,807 dòng)
   - Khóa chính: transaction_seq_id (1..284807) được sinh bằng hàm cửa sổ
     ROW_NUMBER() OVER (ORDER BY time_sec ASC, ctid ASC) để giữ nguyên thứ tự gốc.
   - 4 khóa ngoại: date_key, hour_key, amount_band_key, channel_key.
   - Các độ đo (Measures): time_sec, amount, amount_log1p = LN(1 + amount),
     class_label (0/1), max_abs_v_zscore = GREATEST(|V1|, ..., |V28|), cùng
     28 cột đặc trưng gốc v1..v28.
   - 3 cờ Chất lượng dữ liệu (Data Quality Flags) chuyển hóa từ Phần A của Khang:
     + is_duplicate (DQ-01): Đánh dấu 1,081 dòng trùng lặp dư ra trên cả 31 cột
       (giữ dòng đầu tiên is_duplicate = FALSE cho 283,726 dòng duy nhất).
       Nhờ vậy, kho dữ liệu vừa bảo toàn 100% 284,807 dòng thô, vừa cho phép
       truy vấn tập đã khử trùng chỉ bằng điều kiện WHERE is_duplicate = FALSE!
     + is_zero_amount (DQ-02): Đánh dấu 1,825 giao dịch có Amount = 0 (hành vi
       thử thẻ / zero-amount authorization).
     + has_extreme_v_z10 (DQ-06): Đánh dấu 1,924 giao dịch có ít nhất 1 thành
       phần |V1..V28| > 10.
   - Các cột tích hợp điểm mô hình (Model Score Columns): split_role,
     iforest_score, lof_score, ae_recon_error, logreg_prob, lgbm_prob,
     daily_alert_rank, is_top100_daily_alert, selected_model_name.

2) Bảng chiều 1: Dim_Date (2 dòng — Ngày tương đối)
   - date_key = FLOOR(time_sec / 86400)::INT (nhận giá trị 0 hoặc 1).
   - Phục vụ trực tiếp câu hỏi kinh doanh: "Ngân sách rà soát 100 giao dịch
     MỖI NGÀY" (tức 100 giao dịch cho Relative Day 0 và 100 giao dịch cho
     Relative Day 1, tổng cộng 200 giao dịch rà soát trong 48 giờ).

3) Bảng chiều 2: Dim_Hour (48 dòng — Giờ tương đối 0..47)
   - hour_key = FLOOR(time_sec / 3600)::INT (nhận giá trị 0..47).
   - Chứa thuộc tính phân cấp: date_key (0..1), hour_in_day_offset (0..23) và
     day_cycle_label (4 khung 6 tiếng tương đối mỗi ngày) để thực hiện thao tác
     Roll-up / Drill-down từ Ngày -> Chu kỳ 6h -> Từng giờ tương đối.

4) Bảng chiều 3: Dim_AmountBand (7 dòng — Dải giá trị giao dịch)
   - Chia cột Amount thành đúng 7 dải khớp 100% với phân tích EDA của Khang (A):
     + Key 1: '0'          (Amount = 0)
     + Key 2: '(0, 1]'     (0 < Amount <= 1)
     + Key 3: '(1, 10]'    (1 < Amount <= 10)
     + Key 4: '(10, 50]'   (10 < Amount <= 50)
     + Key 5: '(50, 200]'  (50 < Amount <= 200)
     + Key 6: '(200, 1000]'(200 < Amount <= 1000)
     + Key 7: '> 1000'     (Amount > 1000)

5) Bảng chiều 4: Dim_Channel (3 dòng — Kênh giao dịch MÔ PHỎNG / SYNTHETIC)
   - Được thiết kế thêm (bên cạnh 3 chiều thực tế trên) để làm phong phú cấu trúc
     Star Schema, nhưng tuân thủ tuyệt đối tính trung thực học thuật: có cột
     is_synthetic = TRUE và ghi chú rõ đây là chiều phân bổ tất định (deterministic
     modulo hash) chỉ dùng để minh họa kỹ thuật JOIN đa bảng, tuyệt đối không
     dùng để huấn luyện mô hình hay rút ra kết luận nghiệp vụ thật.
